# DEVELOPMENT

Maintainer guide for local runtime foundation checks and container bootstrap preparation.

## Purpose

- bootstrap the Python package locally
- build a local container image from the current working tree
- prepare a separate dev runtime folder outside the repository
- preserve local `.env` and compose files instead of overwriting them
- support this repository as the deployment and controlled database-correction workspace

## Deployment And Database Correction

This repository owns the Curatarr deployment/commissioning and correction procedure as well as application development. That does not transfer ownership of Ryot, Radarr/Sonarr or Jellyfin internals to Curatarr: inspect and update connected services through their supported APIs, within an explicitly reviewed scope. Do not patch their database tables directly or inspect sibling source repositories without authorization.

### Deployment Handoff

The coordinated movie release is specified in [System Architecture](../../documentation/System%20Architecture.md#coordinated-movie-release--build-specification); work packages/gates are in [Roadmap](../ROADMAP.md#coordinated-release-implementation-plan). Before cutover, rehearse additive workflow migration on a consistent copy, retain the existing IMDb source as a protected handled baseline, review historical watched imports separately and verify source event/recovery compatibility. Current image/entrypoint is scaffold: the new dedicated runtime must start HTTP plus exactly one bot poller and its durable workers, pass image/startup/restart/restore tests and expose useful liveness/readiness without secrets.

Provider retirement is coordinated: preserve current configuration and event boundaries; disable the legacy Ryot Jellyfin writer before activating Curatarr native-viewing writes, retire Ryot-to-Arr and native list acquisition paths as agreed, and verify no competing writers. Neither source baseline nor disabling an import list removes existing movie records. A shadow receiver performs no provider mutations. The final group stays on hold until a good working copy is accepted. Rollback first stops new writers, reconciles uncertain external effects/cursors, then restores compatible runtime/data; do not blindly replay buffered events or merely restore SQLite while assuming provider mutations vanished.

Selected target (2026-10-24 planning): a dedicated Curatarr Docker container on the existing media-services host beside the Arr containers. Keep the exact installation host/volumes/credentials in private deployment material. The Mac remains the test runtime until acceptance. The final shared Telegram group already exists; preserve the test destination until a good working copy is verified and an explicit move is executed. Stable external HTTPS routing and persistent configuration/workflow volumes remain deployment tasks, not completed infrastructure.

1. Read the current workflow, collection contract, configuration template and release guide. Verify the actual worktree, executable CLI and image/compose behavior; scaffold assets are not a production release. The current commissioned test runs on a Mac, not the target server.
2. Identify the target host, persistent configuration/data locations, bot identity, HTTPS endpoint and service reachability. Ask before touching paths outside this repository. Keep tokens and installation mappings in private deployment material, never tracked examples.
3. Preserve and back up the workflow SQLite database, provider data and existing configuration before migration. Use a consistent SQLite backup or stop writers; copying a live SQLite main file alone can omit journaled changes. Validate restore procedures before a substantial correction.
4. Run configuration validation and provider read-only checks, including a protected Ryot user-state query. Schema access alone does not establish that a token can read the household account.
5. Run one Telegram poller per bot token. Keep the same persistent workflow database across web/polling restarts. The default container command validates configuration; explicitly select the required runtime command rather than assuming the image starts the Mini App or poller.
6. Use durable HTTPS hosting for server deployment, retain Telegram launch-data validation, and verify admin versus standard-user access. Temporary Mac tunnels are commissioning tools and can break when the Mac sleeps; a new tunnel URL requires updating the Telegram Mini App launch target.
7. Verify browsing, provider reads, maintenance, backup/restore and process restart behavior. Do not enable scheduled writes or change the shared Telegram destination implicitly. Release publication remains a separate decision.

### Correction Handoff

1. Start with a complete successful read-only reconciliation scan and retain the timestamped report privately. A failed/partial scan cannot authorize absence-based corrections. The scanner's eight rule categories are implemented checks, not proof that every possible inconsistency is covered.
2. Classify the discrepancy and its authority: Ryot owns durable intent/history; Arr owns acquisition target/file/profile/monitoring facts; Jellyfin owns indexed playback/audio evidence. Use Radarr's IMDb/TMDB identity as the acquisition reference, while blocking duplicate or contradictory identities. Never merge different Ryot titles/history based on title similarity.
3. Present a fresh exact candidate set, proposed provider/API changes, evidence, exclusions, backup/recovery and verification plan before a batch, and obtain scoped go-ahead before execution. The household approved the factual acquisition-history backfill approach for qualifying exact matches with Radarr imported-file evidence, but explicitly withheld immediate correction of all cases. That approach approval is not standing batch-execution permission or approval for arbitrary collections, identity rewrites, viewing/rating changes, deletions, monitoring/profile changes or downloads. No batch executor is implemented; do not invent a CLI flag or claim a dry run applied corrections.
4. The existing per-movie repair adds only Previously acquired to an exact non-archived Ryot movie after a fresh complete scan confirms the Radarr imported-file record. Radarr database evidence suffices for this historical acquisition fact; no network-drive verification is required or claimed. Registration alone is insufficient. Confirm the configured user's existing custom collection and preserve every other membership and viewing event.
5. Implement and run any future commissioning batch outside the Mini App, using additive/idempotent operations, conservative limits, durable audit, revalidation immediately before writing and provider read-back afterwards. Account for partial completion: job acceptance or a timeout is not proof of success or failure. Stop on ambiguous identity, ownership or unavailable evidence; retain unresolved cases for external review.
6. Rerun reconciliation and compare the proposed versus verified changes and remaining exceptions. Preserve backups, audit and private evidence. Do not close findings merely to reduce the count, and do not turn unresolved acquisition history into Deleted or Archived by inference.

There must be no in-app batch correction control. Routine viewing input belongs in Viewing inbox; low-volume synchronization belongs under Admin; complex repairs and commissioning datasets are handled here. Controlled archive is a separate, not-yet-implemented workflow that explicitly confirms managed-file deletion and Arr-record removal, preserving Ryot catalogue/history.

## Script Boundary

`maintainer/development/dev-build.sh` is a template helper. Review and adapt these assumptions before relying on it:

- the repository root is resolved from `../..`
- the Dockerfile lives at `maintainer/docker/Dockerfile`
- the runtime folder defaults to `<repo-parent>/<project-slug>-dev/`
- the runtime env file uses `PROJECT_IMAGE=` as the image reference key
- the container defaults to config validation; Telegram polling is an explicit opt-in command

- `docker/compose/docker-compose-dev.yml.example`

## First Run

1. Create a local virtual environment if needed.
2. Install the package with `pip install .`.
3. Copy `config.yaml.example` to `config.yaml` outside the repository or into a local ignored runtime folder.
4. Run `curatarr --config /path/to/config.yaml --check-config` to validate bootstrap-level wiring.
5. Review `docker/compose/docker-compose-dev.yml.example` and `docker/compose/.env.dev.example`.
6. Run `bash maintainer/development/dev-build.sh` to build the image and prepare the external runtime folder.
7. Edit the generated runtime `config.yaml` and `.env` before starting the dev container for real work.

## Telegram Search/Decision Runtime

Install the package, configure permitted positive Telegram user IDs and the service credentials in a local ignored runtime configuration, and add `tmdb.api_key` using `${CURATARR_TMDB_API_KEY}`. The TMDB credential may be a v3 API key or an API Read Access Token (JWT or explicitly prefixed with `Bearer `). The Ryot URL must be its full GraphQL endpoint. Existing Ryot query compatibility must be checked against the deployed Ryot version; fixture tests do not establish compatibility with every release.

```bash
curatarr --config /path/to/config.yaml --check-config
curatarr --config /path/to/config.yaml --run-telegram --database /path/to/data/curatarr.sqlite
```

The bot uses long polling and requires an internet connection to Telegram/TMDB and access to Ryot/Radarr. Run only one polling process for a token and ensure that token is not configured for webhook delivery. This command does not delete existing Telegram webhooks or discard queued updates. Use a dedicated development bot token for commissioning.

For the tested Ryot deployment, the GraphQL route is `/backend/graphql`, rather than the web UI root. Ryot needs a valid user/session token for protected library queries; a successful schema query alone does not prove authentication. The read adapter pages through `userMetadataList`, batches metadata details, and matches exact external identities because Ryot text search covers titles/descriptions rather than external IDs. Positive identity resolutions are cached in memory; user state is fetched again for each decision. Unknown identities require another catalogue scan, which can make first or missing-title lookups slower on large libraries. Invalid or incomplete API responses raise errors instead of silently reporting a title absent.

The [Ryot Collection Contract](../../documentation/Ryot%20Collection%20Contract.md) owns the custom collections, native Owned/Completed boundaries, maintainer handoff, and reported completed Ryot setup. The adapter reads explicit Library, Previously acquired and Deleted, without mapping native Owned to acquisition. New collection keys default to canonical names for existing local configurations; legacy owned is ignored. Configuration rejects duplicate custom names and native collection aliases. Current deletion display reads durable Ryot membership or exact-identity verified local audit evidence, preserving current-copy/outage safeguards and surfacing missing membership as synchronization drift. Automatic maintenance of the six custom collections is not enabled; the separate optional native movie Owned policy is described below. Unresolved historical acquisition exceptions remain unresolved. Normal API collection operations were verified by the Ryot maintainer on v10.5.0 Community, not by this runtime's fixture tests.

In a private chat as a configured user, send `/start`, then `/movie <title>` or a plain title. The first ten results are persisted and shown by default as a poster carousel with title/year, a short synopsis, result position, Previous/Next, Select movie, and List view controls. List view retains individual title buttons and can return to the current carousel position. Browsing and toggling do not consume the selection or query Ryot/Radarr. Selecting a movie reads Ryot/Radarr and opens a decision prompt. Replaying a completed selection does not create another decision. On a changed state, the old decision is superseded and fresh actions require a new click. State reads that fail leave the decision open. Acknowledgements and generic error messages contain no service credentials.

TMDB poster URLs and synopses are presentation data and do not affect identity or decision fingerprints. The bot edits photo media while browsing. Switching between photo and text views delivers the new view before removing the old message. Missing artwork or a rejected poster URL falls back to text while preserving navigation and selection. Media captions are bounded to Telegram's 1024 UTF-16-unit limit. Existing saved searches without artwork remain usable with the text fallback.

Only detail refresh and closing a question with `Keep as is` are implemented. Other actions remain open and explicitly report no changes. No acquisition, archive, monitor, or profile writes are enabled. The live runtime currently exposes movie commands only; the read-only Sonarr adapter remains available separately.

SQLite schema version 3 adds the unique viewing-event ledger without discarding prior decisions/cursors; version 2 introduced polling cursors. Back up the workflow database before upgrading and do not downgrade the runtime against it. New search/selection prompts have a 24-hour expiry; legacy search prompts without expiry require a fresh search. Viewing follow-ups deliberately have no expiry. Update offsets are saved after handling; Telegram delivery and SQLite commits are not atomic, so a crash can repeat a response. Acquisition actions remain disabled.

### Viewing Confirmation And Rating

The polling runtime now includes a separate viewing observer with its own SQLite connection/provider reader. It is inactive until an authenticated configured admin sends `/followups_here` in the intended test chat. The bot verifies that destination with Telegram and reads a complete Ryot movie/event snapshot before binding it. A private test chat is explicitly identified as private, not represented as visible to the whole household. For shared testing, bind an actual group/supergroup in which the bot can post. Ordinary movie search remains private-only; viewing callbacks work only for configured household users, in the bound chat, on the recorded prompt. A different destination cannot silently replace the current binding; commissioning ORION needs an explicit migration review.

The first successful snapshot baselines all existing completed movie-event IDs and emits no historical prompts. Subsequent complete snapshots create durable `viewing_followup` questions for newly observed completed IDs, including an existing in-progress event that becomes completed. Account/endpoint identity scopes the ledger; partial scans cannot advance it. A newly imported historical event not present in the baseline is also newly observed and may need human clarification. Schema-only access is insufficient; actual protected history/ownership must validate.

Detection runs every `telegram.viewing_scan_interval` (default `5m`) while the poller runs and delivery is enabled. This viewing observer is separate from the implemented daily read-only system maintenance worker. At most five queued prompts are attempted per scan, and overflow remains queued. `/followups_stop` in the bound destination pauses observation/delivery without closing questions. Re-enabling preserves the baseline and outstanding questions. No destination is inferred from an allowed user ID; no ORION channel is automatically selected.

Each new prompt includes a poster when an exact TMDB movie ID provides artwork, and the native viewing date when recorded. Missing artwork falls back to text without blocking the question. Replies edit the same message, using Telegram's cached photo identifier. Each native viewing event has a separate prompt, even for repeat watches of the same movie; ratings link to that event, not another watch.

Each shared viewing request snapshots the configured household users (admins plus standard users) and records their temporary answers, names and timestamps in its context/audit. These are workflow responses, not personal watch histories. Buttons are Yes, I watched this / No, I did not watch this. One No hides that request from that user and leaves everyone else pending. The first Yes confirms the existing household event immediately and removes the request from all other inboxes, independent of rating completion. Only the confirming respondent can optionally rate, accept an existing rating or choose No rating. Stale replies cannot undo a Yes or submit another person's rating. Repeated No answers never count as multiple people; silence is never No. When every snapshotted participant says No, the item moves to Admin → Declined viewings, preserving native history. Admins can freshly validate and confirm it there; rating is then optional for that admin. Native history deletion is available only through the explicit admin reset below; retention execution remains disabled. Legacy disputed questions have no proven unanimous vote and return to ordinary confirmation. Existing confirmed questions recover their respondent from the confirmation audit during policy adoption; existing questions, baselines and uncertain-operation text are retained. Participant snapshots remain fixed across restarts/config changes. A request whose original native event was removed becomes a monitored technical finding; the retained maintainer diagnostic group offers Clear stale request. An exact native event no longer COMPLETED and interrupted history resets belong in the same group. Positively verified mismatches are excluded from the ordinary viewing inbox/count without an additional notice; restored valid events rejoin the appropriate queue. Provider outages/identity uncertainty do not establish absence or hide an unverified request. That local-only action rechecks the exact account, movie identities and a complete duplicate-free history, rejects a restored event, provider failure or pending rating operation, and audits closure without confirming a watch or changing Ryot. It never closes requests automatically.

Normal Admin → Declined viewings shows exact-TMDB-ID posters, Confirm household watched and Review again. Technical viewing repairs are not part of normal use. With maintainer diagnostics explicitly enabled, Declined viewings and Sync issues → Viewing requests retain their poster-backed correction cards. Four diagnostic actions remain visible; unavailable actions are grey with a reason: Confirm household watched, Review again, Clear viewing history, and Clear stale request. Review again requires the original native event, audits previous votes, resets participants to current configured users and reopens that same event without creating a watch or removing reviews. Clear stale request remains local-only and requires the original event to be absent.

Clear viewing history is a separate destructive admin action: `/api/maintenance/viewing/reset-preview` freshly validates account/movie/event/collection identities and issues a snapshot-bound confirmation token. The confirmation dialog names the movie and counts **all viewing records, including repeat watches**. Only explicit confirmation through `/api/maintenance/viewing/confirm-declined` removes them. Reviews/ratings and other collection memberships, including Library, must remain unchanged. Completed/InProgress flags and newly generated Monitoring flags are removed so the result reads unwatched. This is not media deletion or archive authorization.

Ryot v10.5.0 [deleteSeenItem](https://github.com/IgnisDa/ryot/blob/v10.5.0/crates/services/miscellaneous/progress/src/lib.rs) invokes [post-seen collection updates](https://github.com/IgnisDa/ryot/blob/v10.5.0/crates/utils/dependent/seen/src/lib.rs), which can remove Watchlist and add watched/progress flags. Therefore a movie with history and existing Watchlist/Monitoring membership is blocked for manual review rather than changing that intent. Native default collection ownership and exact IDs are checked before writes.

A complete original snapshot and operation intent are persisted before mutation in the existing state snapshot store; no schema change is required. A five-minute claim, exact context checks and pending-rating guards prevent competing workflow writes. Every retry reads native state and can delete only unchanged records from the original snapshot; new history or changed reviews/memberships stop the operation. Async flag-job intent is persisted before submission and is never blindly resubmitted after an unknown outcome. Pending resets block normal answers/observer work for that movie. Explicit admin retry reconciles the same operation; there is no automatic reset executor. A lost job or changed native state may need manual investigation. Completion requires empty history, cleared flags and preserved reviews/intent, then audited local closure and fixed-message Telegram refresh. Tests use synthetic native writes; live destructive acceptance remains pending.

The viewing adapter supports Ryot's native OUT_OF_FIVE and OUT_OF_HUNDRED preferences. Domain ratings and API read-back remain normalized to 0-100: a new question's score is multiplied by twenty, and a legacy 0-10 score by ten. For OUT_OF_FIVE mutation input, the adapter divides that normalized value by twenty; for OUT_OF_HUNDRED it sends the normalized value directly. Thus 4/5 sends 4 or 80 respectively, with stored/read-back value 80 in either case. Legacy 9/10 sends exactly 4.5 under OUT_OF_FIVE. Curatarr does not change preferences or reinterpret historical ratings. Other native scales fail closed. Supported preference changes preserve baselines, questions and same-score retries; a preference change during a write can leave a mismatched unconfirmed review requiring external investigation, without falsely resolving the question or creating another review.

Existing linked reviews are preserved: an authorized respondent can accept the recorded rating, displayed on the question's scale without rounding, but replacing a different linked review is external work. New private review text identifies Curatarr, the movie, recorded viewing date (or Not recorded), the signed Telegram display name of the rater and a short event-specific reference. The shared Ryot account remains the review author; Curatarr retains the Telegram user ID in its audit. Existing reviews and already-started recovery text are not rewritten. The exact text is persisted with the local operation before writing so title/date changes cannot break retry recovery. Older uncertain operations retain their original technical marker; existing reviews are not rewritten. Read-back must verify account, event, identity, review linkage and normalized rating before closing the question. Generic Ryot state writes remain disabled.

Provider reads and upstream v10.5.0 behavior were checked: [review creation](https://github.com/IgnisDa/ryot/blob/v10.5.0/crates/utils/dependent/review/src/lib.rs) scales input according to account preferences, and [watch updates](https://github.com/IgnisDa/ryot/blob/v10.5.0/crates/services/miscellaneous/progress/src/lib.rs) only change supplied optional fields. The rating-link request supplies only seenId and reviewId, not viewing dates/progress. Fixture tests do not replace live mutation commissioning or guarantee compatibility with other releases.

Delivery is claimed durably before sending. A timeout/crash may mean the message arrived: do not automatically resend sending/uncertain questions. An authenticated callback in the bound chat can recover the missing Telegram message ID; otherwise the unresolved question remains in maintenance for external investigation. Rating operations are also marked before creation; retrying the same score reconciles the marked review and never issues a second create after an uncertain attempt. Different scores or decline are blocked while an earlier write is unconfirmed. Audit records capture request, responder, event and verified outcome. The observer never adds watched events, edits profiles/monitoring, downloads, archives or deletes media.

Detection currently observes completions already recorded in Ryot. The previously disabled Jellyfin-to-Ryot integration is not enabled by this change. Commission a genuine new Ryot completion and its authorized rating reply before declaring live end-to-end success; do not inject fake household history simply to populate the screen.

Offline verification:

```bash
PYTHONPATH=src .venv/bin/python -m unittest discover -s tests
```

Tests cover search-to-selection-to-revalidation, simulated viewing detection/replies and native rating conversion, authorization, expiry, forged actions, replay, restart persistence, partial-write recovery, API sanitization and CLI startup. Movie search, Mini App reads and the complete viewing snapshot have been checked live read-only. Earlier private-test delivery and respondent-approved native ratings succeeded; the user subsequently accepted the five-point grading flow. The new OUT_OF_FIVE adapter path still needs a respondent-authorized live rating check; disputed-message acceptance, live repeated watches of the same title, and actual shared-group commissioning remain pending. See the [feature register](../FEATURES.md) for current capability and acceptance gaps. Acquisition/profile writes now exist; unified retention remains incomplete. NFO enrichment stays deferred.

## Settings And Owned Cleanup

The admin-only Mini App **Admin → Settings** page contains a Name field, the movie-only **Automatic Owned cleanup** policy, and two independent Telegram message-cleanup switches. Default name is **Household**. Save an installation-specific name there; there is no Telegram rename command or conversational naming setup. The display name is shared by the web/polling processes through SQLite and appears in Mini App scope labels, Telegram viewing prompts/help, and new review provenance. Internal shared_household/account/event keys and existing review text remain stable. Name changes during an uncertain rating operation cannot alter its persisted recovery text.

Cleanup defaults to **off**. Switching it on directly authorizes removing Owned from all verified movie entries in the configured account's native Owned collection; there is no first-run preview/approval. Series and other entity types are excluded. No other collections, watch events, reviews, acquisition settings, or media files are changed. Owned is never repurposed as acquisition history, and uncertain acquisition facts are not backfilled. This opt-in policy is the exception to the default preservation of native Owned membership; the system collection itself remains.

The separate automation worker runs with `--run-telegram`, independently of viewing-follow-up activation. It checks for due work every 30 seconds and runs the Owned policy at most once per 24 hours, including across restarts. Explicit off/on activation can start a new run earlier. The verified account/collection is pinned for that activation; a changed account cannot inherit the enabled policy without re-enabling it. A web-only runtime can save the setting but does not execute jobs. Disabling stops future work; work already underway may finish. The UI shows one last-run line; the info icon provides these scope/cadence details. It exposes no generic batch-repair interface.

Before a submission, the adapter verifies configured-account ownership of the native Owned collection, complete count-consistent pagination, exact metadata IDs and movie types. It retains each candidate's membership extra information locally. Partial, duplicate or identity-inconsistent snapshots cannot authorize a submission. A durable run claim prevents overlapping scans from submitting stale results; a pending operation and audit snapshot are committed before Ryot's remove-membership job is requested. Job acceptance is not completion. Read-back verifies absence of the exact candidate IDs before reporting removed counts. Pending/uncertain jobs are checked again after five minutes and are never blindly resubmitted. A partial job remains visible as awaiting verification; disabling/re-enabling does not discard its record. Existing audit/database backups preserve recovery evidence, though re-adding membership cannot promise original provider-managed timestamps/ranks.

The installed v10.5.0 collection-removal API and source were checked; a live read-only snapshot validates the new reader. Offline transport tests cover completion, partial jobs, response loss/restart, overlapping scans, daily cadence, disabled policy and non-movie preservation. Native removals remain unexercised until an admin enables the switch; fixture verification is not a claim that a live cleanup has already run. Ordinary metadata/progress updates were not established as a universal Owned-on-add rule; selected Ryot Yank integrations can populate Owned when their separate sync flag is enabled. Do not silently alter those integrations.

Installation settings and run/audit state reuse existing tables without a schema migration. Settings writes are authenticated/admin-only, revision-checked, strictly validated and audited. A display name is rendered as text, never HTML. Credentials and service configuration remain outside this page.

The **Remove answered prompts** and **Remove unanswered prompts** switches are independent and default to off. Each applies 36 hours after the original message was sent, not after the latest reply. A unanimous decline is an answered prompt even while its admin-review record remains open; a single No while others remain pending is unanswered. The timeout was explicitly changed from the requested 72 hours because [Telegram permits deletion only while a message is less than 48 hours old](https://core.telegram.org/bots/api#deletemessage). No chat-wide auto-delete setting is changed. A long outage past that window can leave older messages undeletable. New deliveries record their native send time; legacy confirmed deliveries can use their exact decision-specific delivery audit. Unknown-age/uncertain sends are not guessed. Up to five messages are attempted per worker pass; transient failures retry only the same exact message ID, and already-missing responses are treated as removed. Last-run counts distinguish removals, unavailable requests and skipped messages.

Message cleanup never resolves/expires a question, clears a rating operation, or changes Ryot history. A removed unanswered prompt remains under Viewing inbox with **Reopen in Telegram**. That action, available to all configured users, verifies the current movie cursor, original event/account and destination binding, and queues the same question for the next viewing check; it does not create another watch/question. A different message ID invalidates old callbacks. Unanimously declined events remain in Admin review and cannot be reopened as ordinary prompts; older unassigned disputes can be answered again without inventing historical votes. An uncertain deletion followed by a long outage remains explicitly recoverable through reopening. Sent messages use distinct WATCH CONFIRMATION REQUEST / RATING REQUEST / VIEWING CONFIRMED / VIEWING DECLINED caption banners. Existing open messages can receive the banner through a verified fixed-message edit; missing messages are not silently replaced.

## On-Demand Movie Reconciliation

Run a fresh snapshot comparison and persist admin findings locally:

```bash
PYTHONPATH=src .venv/bin/python -m curatarr.cli --config /path/to/config.yaml --database /path/to/curatarr.sqlite --reconcile-movies
```

Use the same persistent SQLite file as the application to share its decision queue. Back up the workflow database before initial commissioning. Provider access is read-only, but the command writes local job records, findings, and technical issues. It needs Ryot and Radarr access, not TMDB credentials, Telegram polling, or a running web server. Output is an admin-facing JSON report containing titles and typed IDs; keep it private. It never prints raw provider exception text or credentials.

- Every invocation reads fresh complete provider snapshots before returning findings. Repeated unchanged findings retain IDs across restart; changed evidence supersedes old findings, and complete successful scans resolve obsolete ones.
- Findings use existing `pending_decision` rows with `reconcile:` types, `admin` audience, and no search-prompt expiry. The admin Mini App maintenance session consumes this shared queue. No new table/schema version is required; initialization adds a scoped unique index without discarding prior data.
- `counts` reports provider movie totals separately, not a deduplicated household total. `movies_requiring_attention` counts provider records with open findings; `finding_count` counts reasons, so one movie can contribute several reasons. Ambiguous duplicate records remain separate until identity review.
- `revalidated: true` means the complete latest scan succeeded, at `observed_at`; it is not an indefinite freshness guarantee. `last_validated_at` and `last_validated_run_id` retain the last complete validation when a later scan fails or is interrupted. Exit status is zero only for a successfully revalidated report. Failed or superseded scans return nonzero. Stored reports are historical; rerun before review.
- Provider outages, incomplete pages, malformed records, or missing runtime evidence preserve earlier findings as unvalidated and create deduplicated technical issues. Ryot queries explicitly request TITLE/ASC ordering, verified against the installed v10.5.0 schema; repeated metadata across pages still invalidates the snapshot instead of being silently deduplicated. Ordering is not a remote transactional snapshot, so avoid concurrent catalogue changes and revalidate before future corrections. Newer scans prevent older overlapping scans from publishing stale results. An interrupted process can leave a running job; a fresh invocation can proceed and supersede it.
- Matching uses exact typed external IDs. Title-only, duplicate or conflicting matches require review. Cross-resolution and confirmed local mappings are not yet integrated into this scanner; no exact match is not proof of absence.
- Missing/unmonitored means Radarr reports this combination. A reported file does not prove storage is accessible. No filesystem, mount-health, Jellyfin readiness, or physical-deletion checks are performed, and no acquisition/deletion history is backfilled.

The scan does not change collections, monitoring, profiles, Arr entries, files or download queues. Suggestions are text only (`actions_enabled: false`). The diagnostic Mini App session and skip/resume controls remain available behind the off-by-default maintenance.show_diagnostics flag. The separate system maintenance worker below now schedules read-only checks; automatic repairs remain unimplemented. See System Architecture, Flow 9, for rule coverage and safeguards.

### Operational Boundary

Curatarr is the intended daily entry point for the household. Its ordinary search/viewing/rating choices should use protected workflows. Unexpected drift from outages, interrupted operations or direct edits must be detected and alerted, with technical diagnosis/repair performed by the repository maintainer. Do not add a repair flow for every detected category. Recurring real-world problems may justify a separately approved, simple household workflow later. Detection and workflow guards reduce risk; they do not guarantee database consistency across independent services.

### System Maintenance Check

Ryot metadata readiness is separate from catalogue association and collection membership. The current monitor does not audit native `isPartial` status. Ryot metadata-detail responses are cached: a stale partial flag can keep the native title-refresh animation active even when the stored metadata is ready. During commissioning, validate readiness separately from import-job success; if necessary, a scoped maintainer check may expire the returned metadata `cacheId` through the supported API and re-read the same exact record. Never infer a database-wide failure from cached flags, launch a bulk refresh by implication, or force a partial flag clear when the provider record is unavailable. Preserve user history and memberships while diagnosing refresh state.

Normal Admin → Sync issues shows only **Maintenance needed: Yes / No**, last checked and Check now. Technical viewing requests are monitored but have no normal Mini App workflow. No library category browser or acquisition Correct button is shown. All eight existing categories, endpoints, persisted evidence and per-admin skip/filter progress remain intact. `maintenance.show_diagnostics: true` restores the old diagnostic browser for maintainer use; it defaults to false and is deliberately absent from household Settings. Hidden/skipped findings still affect maintenance status. Diagnostic endpoints remain admin-only. Technical repair POSTs (acquisition correction, stale-request closure, history reset and reset preview) additionally require the maintainer flag; normal mode rejects them with 403 even if an old UI or direct request tries to invoke them. Household confirm/Review again remains available without that flag.

A dedicated worker runs independently of Telegram answers, viewing observation and write-capable cleanup policies.
